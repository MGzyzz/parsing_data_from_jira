## 1. Суть проекта

**Проблема.** Нет достоверного источника, какой релиз стоит на какой среде. Колонка `Release` в реестре сред заполняется руками и неактуальна: почти везде `release 57/3` или `release 59`, хотя фактически стоит `Release 68 + HF`. Реальную версию вычисляют вручную по тегам образов в кластере. Из-за этого теряется время перед накаткой и при разборе инцидентов, реестр нельзя использовать как источник правды, нельзя быстро ответить заказчику.

**Задача.** Сервис на Go, который **раз в час** определяет релиз на каждой среде по тегам образов и сам проставляет его в колонку `Release` реестра сред в виде `Release 68` или `Release 68 + HF`.

**Возможное имя репозитория:** `redo/devops-tools/env-release-tracker` (открытый вопрос).

## 2. Правила работы (обязательные)

- **Коммиты без атрибуции модели.** Запрещено `Co-Authored-By: Claude ...`, `Claude-Session:`, «Generated with Claude Code» и любые подписи модели.
- **Пайплайны GitLab пока НЕ запускаем** (решение 2026-09-15). Реализация `ImageCollector` — заглушка на тестовых данных; боевой запуск подключается позже отдельным решением.
- **Запись только в копию реестра.** Боевой `SHEET_ID` в конфиг разработки не попадает.
- **По умолчанию dry-run.** Запись в таблицу требует явного флага `-write` — случайный запуск не должен ничего изменить.
- **Jira — ТОЛЬКО ЧТЕНИЕ.** Никаких изменений: ни создания, ни редактирования, ни удаления, ни переходов статусов, ни комментариев. Защита — белый список эндпоинтов в `http.RoundTripper`, а не дисциплина. `POST /rest/api/2/search` — читающий вызов, поэтому правило «только GET» не годится.
- **MEMORY.md ведётся постоянно.** Значимые решения фиксируются здесь.

## 5. Архитектура

### 5.1 Главное: источник правды — НЕ Jira

**Версия на среде определяется тегами образов в кластере**, а не задачами в Jira. Роль Jira — **сверка** и базовые теги релизов.

```
Реестр сред (Google Sheets)          ← читаем список сред
        │  строки со статусом active | configuring (~104 среды)
        ▼
GitLab pipeline collect-images       ← ЗАПУСКАЕМ на каждую среду
        │  читает образы подов namespace
        ▼
   images.json (артефакт джобы)      ← ["redo-backend:main-1.29.13", ...]
        │
        ▼
   Вычисление релиза: N = minor + 39
        │
        ├──► Jira (только чтение)    ← сверка с задачами "Release N" и HF
        │
        ▼
Реестр сред, колонка G «Release»     ← ЗАПИСЫВАЕМ «Release 68 + HF»
```

### 5.2 Правило номера релиза

Теги имеют вид `main-1.<minor>.<patch>`. **Релиз двигает minor, HF двигает patch.**

**`Release N` ⟷ `minor = N − 39`** (переменная `RELEASE_MINOR_OFFSET=39`)

| Релиз | Теги кор-сервисов |
|-------|-------------------|
| Release 59 | `main-1.20.x` |
| Release 66 | `main-1.27.x` |
| Release 67 | `main-1.28.x` |
| Release 68 | `main-1.29.0` |
| HF после 68 | backend `main-1.29.13`, camunda `main-1.29.12`, front `main-1.29.20` |

Правило держится минимум с Release 59, но **исключения возможны** — поэтому Jira нужна для сверки.

**Кор-сервисы** (только по ним считается номер релиза):
`redo-nuxeo`, `redo-backend`, `redo-camunda`, `redo-front`, `redo-integration`

**Алгоритм для среды:**
1. У сервиса в подах два тега (идёт накатка) → берём **больший**.
2. `N = minor + 39` по кор-сервисам. Если minor у кор-сервисов **разный** → берём **меньший** и помечаем расхождение.
3. `+ HF` — если хотя бы один сервис новее своего тега в задаче `Release N`:
   - **кор-сервис:** patch выше базового тега из задачи (задачи нет → выше 0);
   - **не-кор сервис:** тег новее, чем у него в задаче `Release N`. **Правило N−39 к ним НЕ применяется** — у них своя нумерация (в Release 67: `redo-email main-1.9.6`, `redo-event main-1.24.0`, `redo-calendar main-1.26.0`), только сравнение с Jira. Нет в задаче → на HF не влияет, пишется в детали.
4. В расчёте участвуют все сервисы namespace с тегом `main-1.x.y` или `release-1.x.y`, включая суффикс cherry-pick (`main-1.28.1-mcp4-8164`). Образы с другой схемой (`redo-ai`, `busybox`, инфраструктура) — не в расчёт, но в детали.

**Сверка с Jira:** задача `Release N` существует; базовые теги кор-сервисов совпадают с `main-1.(N−39).base`; теги с patch выше базы встречаются в каком-либо HF после `Release N`. Несовпадение → предупреждение в лог + пометка о расхождении, **значение всё равно записывается**.

### 5.5 Источник: Jira (только чтение)

- Инстанс **Server / Data Center** (`deploymentType: Server`) → API `/rest/api/2/`, `Authorization: Bearer <PAT>`, email не нужен, `description` приходит **плоским текстом** (wiki markup), не ADF.
- JQL: `summary ~ "Release" AND project = DevOps` — сейчас **447 задач**.
- Доступ — **отдельный технический токен, не личный**.
- Заголовки: релиз `Release 68 ...`, `Release 57/3 ...`; хотфикс `HF Release 11 Сентября ...`, `HF ... Release 12 Июня BAITEREK`.
- Теги — в секции `Projects:` описания задачи. Пример (DOPS-4820, Release 68):

```
*Projects:*
 # nuxeo: main-1.29.0
 # backend: main-1.29.0
 # esedo-gateway:
 # -enbek-integration: main-1.29.0-
 # redo-email: main-1.29.0
```

- У HF в `Projects` **только изменённые сервисы** (DOPS-4892: `redo-backend main-1.29.13`, `redo-camunda main-1.29.12`).
- **Дата события** — поле `Date` из описания; нет → `created`.

### 5.6 Грязные данные Jira — разбор на стороне сервиса

Конвенцию для задач накатки **не вводят**, JQL остаётся как есть. Отличать релизные задачи от шума — задача сервиса.

| Особенность | Как обрабатывать |
|-------------|------------------|
| Имена то короткие (`backend:`), то полные (`redo-backend:`) | **Нормализовать к имени образа** |
| Зачёркнутые строки (`-текст-`) | Сервис исключён — **пропускать** |
| Пустой тег (`esedo-gateway:`) | **Пропускать** |
| Жирный текст вокруг строки (`*...*`) | **Снимать разметку** |
| Несколько блоков `Environments` + `Projects` в одной задаче | Разные теги на разные среды. DOPS-4820: основной поток `main-1.29.0`, а `prod-holding` и `prod-idfrk` — `release-1.29.1` |
| Хвосты-комментарии после тега | Брать **только первый токен** |
| Шум под JQL | «Main / Release: проставить всем пользователям единый пароль», «Включить конфиг ... на release», «Release PLAT-7484 для сред ...» |

**Признаки настоящей релизной задачи** (не исчерпывающе): номер релиза или HF в заголовке; секция `Projects` хотя бы с одним разбираемым тегом; статус `Done`; тег согласуется с правилом `minor = N − 39`.

**Непонятные задачи не роняют прогон** — пропуск + запись в лог (ключ задачи и причина), чтобы список исключений можно было дописать руками.

### 5.7 overrides.yaml — точечные правила по проблемным средам

```yaml
envs:
  sk-prod:
    tags_name: "<раннер SK>"
  prod-devops:
    skip: "среда выключена"
  dev:
    skip: "офисная среда, теги веток"
  nit-adilet:
    interval: "24h"
```

- `environment` — что передать в collect-images вместо имени из реестра;
- `tags_name` — принудительный раннер. **Проверить:** по документации GitLab переменные при запуске пайплайна приоритетнее `workflow:rules:variables` — подтвердить на нашей инсталляции;
- `skip` — не опрашивать, причину в лог, значение в таблице не трогать;
- `interval` — опрашивать реже раза в час.

**Namespace через переменную не переопределить:** шаблон `set-namespace-before-script` выставляет `NS` в `before_script` и перетирает переданное. Нестандартный namespace — правилом в шаблоне или через `environment`.

**Кандидаты на overrides:** `sk-prod` (нет правила в шаблонах, уйдёт на раннер kt), `prod-devops` (выключена, в реестре active), офисные `dev`/`main`/`hf-main`/`sprint`/`release` (теги веток), `kegoc-test` (проверить namespace), среды `nit` в статусе configuring (не развёрнуты, опрашивать реже).

### 5.8 Запуск

- **Раз в час.**
- Параллельность пайплайнов ограничена, по умолчанию **5**: ~104 пайплайна в час, ~2500 в сутки.
- **Таймаут на пайплайн — 10 минут**; истёк → среда помечается «не удалось снять», прогон продолжается.
- Режим **dry-run**: всё посчитать и вывести в лог, в таблицу не писать.
- Режим **одной среды** — для отладки.
- **Пайплайн упал / раннер недоступен / namespace пустой** → значение в колонке **не трогать**, зафиксировать ошибку.

## 9. Ориентир по стилю: backup-report

`~/Desktop/work/practice/backup-report` — предыдущий проект заказчика с похожим механизмом (сбор данных → Google Sheets, прогон по расписанию). **Следовать его структуре.**

```
main.go                 170 строк — только флаги, сборка зависимостей, сигналы
internal/app/           268 — оркестрация прогона + schedule.go
internal/config/        142 — загрузка конфига
internal/gsheets/       467 — клиент Google Sheets + login.go
internal/parser/        145 — разбор текста + testdata/*.txt (golden files)
internal/report/        245 — формирование отчёта
internal/telegram/      367 — источник данных
internal/dates/          14 — мелкий хелпер отдельным пакетом
```

**Что перенять:**
- Пакет = одна ответственность; файлы небольшие (100–470 строк).
- **Тест рядом с каждым пакетом**, без исключений.
- **`testdata/*.txt` как golden files** для парсера — тесты идут без сети.
- Комментарии объясняют **почему**, а не что: «SIGTERM шлют systemd и docker stop. Без обработки процесс добивают SIGKILL»; «Структура, а не три строковых аргумента подряд: перепутанные местами пути компилятор бы не заметил».
- Флаги `-dry-run`, `-daemon`, `-config`; одиночный прогон по умолчанию, расписание задаёт cron.
- `signal.NotifyContext` + ненулевой код возврата, чтобы cron видел провал.
- `escapeFormulas` — значения из внешнего источника экранируются, чтобы Sheets не принял их за формулу. **Здесь понадобится то же.**
- `context.WithoutCancel` для уборки за собой при отмене контекста.
- Зависимости: `google.golang.org/api`, `golang.org/x/oauth2`, `gopkg.in/yaml.v3`.

**Отличие:** там OAuth от живого пользователя, здесь — **service account** (сервис безголовый, интерактивного логина быть не может).

| Токены (Jira, GitLab, Google) | Утечка в git или логи | Vault; `.env` + `.gitignore`; маскирование `Authorization` в логах + тест |
| Вызовы в Jira | Случайное изменение данных | Белый список эндпоинтов в `http.RoundTripper` + тест «DELETE не уходит в сеть» |
| **Боевой реестр** | Запись в рабочую таблицу при отладке | **Только id копии.** Боевой id не в конфиге разработки. `-dry-run` по умолчанию на время разработки |
| Кэш на диске | Данные компании локально | `.gitignore`, TTL, в Docker — том |
| `testdata/` в git | Реальные данные навсегда в истории | Санитайзер перед коммитом: ключи задач → `PROJ-1`, имена/email → заглушки |
| Запись в Sheets | Затереть чужую правку | Сверка имени в колонке A перед записью; только колонка G; не писать, если не изменилось |
| Нагрузка на GitLab | ~2500 пайплайнов в сутки | `CONCURRENCY=5`, таймаут 10 мин, `interval` в overrides |

**Находки при разборе Jira (шаг 4):**
- В заголовке HF `Release 11 Сентября` — это **дата, а не номер релиза**. Номер у HF не читается из заголовка; привязка к релизу идёт по дате.
- Шум отсеивается требованием цифр сразу после слова `Release`: `Release PLAT-7484`, `Main / Release: проставить пароль`, `Включить конфиг на release` номера не дают.
- В Go `\b` — граница **ASCII**-слова и после кириллического «Среды» не срабатывает. Русские заголовки секций переставали распознаваться; в регулярном выражении `\b` убран.
- Guard разграничивает по **эндпоинтам**, не по методу, и сравнивает путь **без строки запроса** — иначе белый список обходился бы дописыванием параметра. Подпути задачи (`/comment`, `/transitions`) под разрешение не попадают.

**Решения, закреплённые в коде шагов 1-3:**
- Разбор обоих форматов тега — в одном пакете `tag`; иначе правила нормализации разъедутся и сверка начнёт молча не сходиться.
- `Version.Compare` сравнивает числа, а не строки: лексикографически `1.29.9` оказалась бы старше `1.29.13`.
- `ParseProjectLine` различает намеренный пропуск (зачёркнуто, пустой тег, заголовок) и ошибку разбора — нечитаемый тег обязан попасть в лог.
- Из двух тегов одного сервиса берётся больший (идёт накатка).
- При расхождении кор-сервисов по minor берётся меньший + флаг `MinorMismatch`.
- Сверка с Jira не имеет права вето: `JiraMismatch` ставится, значение пишется.
- `Result.Cell()` — единственное место превращения результата в текст ячейки; форматы HF и cherry-pick меняются здесь.
- `config.Load` копит ошибки и возвращает разом; отсутствие `overrides.yaml` — не ошибка, нечитаемый `interval` — ошибка.
