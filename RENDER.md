# Проверка Google OAuth на Render Free без Docker

Инструкция для ветки `google-server-oauth`.

**Для реального прогона `prod-holding` после входа переходите к разделу 8.**
Разделы 1–7 описывают отдельный тест только авторизации.
 Проверяет вход пользователя через
Google на удалённом сервере и сохранение токена. Текущий режим `-google-auth`
не читает таблицу, не пишет в неё и не запускает Jira/GitLab.

**Это одноразовый тест авторизации, а не постоянный деплой tracker.** После
успешного входа процесс завершится. Render может перезапустить его, а локальный
токен при перезапуске потеряется. Не переключайте Start Command на `-daemon`
в надежде использовать этот файл: обычный tracker не поднимает HTTP-сервер,
а Free Web Service требует открытый порт.

## 1. Отправьте ветку в GitHub

Из каталога проекта:

```bash
git switch google-server-oauth
git push -u origin google-server-oauth
```

При `Permission denied (publickey)` сначала настройте SSH-доступ к GitHub
в своём терминале. В Render подключайте именно эту ветку, не `main`.

## 2. Создайте Web Service

В Render Dashboard выберите **New → Web Service**, подключите репозиторий
`MGzyzz/parsing_data_from_jira` и укажите:

| Поле | Значение |
|---|---|
| Branch | `google-server-oauth` |
| Language / Runtime | **Go**, не Docker |
| Root Directory | оставить пустым |
| Instance Type | **Free** |
| Build Command | `GOTOOLCHAIN=auto go build -o env-release-tracker .` |
| Start Command | `./env-release-tracker -google-auth -google-auth-listen 0.0.0.0:$PORT` |
| Health Check Path | оставить пустым: стандартная TCP-проверка |
| Auto-Deploy | отключить на время ручной проверки |

Проект требует Go 1.27.0, как указано в `go.mod`. `GOTOOLCHAIN=auto` позволяет
современному Go загрузить требуемую версию. Если сборка сообщает о недоступном
Go toolchain, проверьте build log и возможность загрузки этой версии; не
понижайте `go.mod` только ради деплоя.

Render сам задаёт `PORT` и обслуживает HTTPS. Nginx, собственный сертификат
и Docker для этого теста не нужны. В приложении есть `/health` (можно указать его вместо TCP-проверки), но нет
главной страницы: HTTP-путь `/` возвращает 404.

После создания сервиса скопируйте **фактически выданный** URL вида
`https://your-service.onrender.com`. Не угадывайте его по имени сервиса.
Если первый деплой уже стартовал без настроек Google и упал, это ожидаемо:
завершите следующие шаги и повторите деплой.

## 3. Настройте Google Cloud

В Google Cloud проекте:

1. Включите **Google Sheets API**.
2. Настройте OAuth consent screen / Google Auth Platform.
3. Для аудитории **External** и статуса **Testing** добавьте аккаунт, которым
   будете входить, в **Test users**.
4. Создайте OAuth client типа **Web application**. Старый **Desktop app**
   для этого режима не подходит.
5. В **Authorized redirect URIs** добавьте:

   ```text
   https://your-service.onrender.com/oauth/callback
   ```

   Замените домен фактическим адресом из Render. Путь должен совпадать точно,
   без завершающего `/`. Authorized JavaScript origins для этого серверного
   сценария не требуются.
6. Скачайте JSON клиента. Он содержит верхнеуровневый объект `web`.

Для будущей проверки записи выбранный Google-аккаунт должен иметь права
**Редактора** на тестовую таблицу. Само OAuth-согласие не выдаёт права на файл.

## 4. Добавьте секрет и переменные в Render

**Environment → Secret Files → Add Secret File**:

- Filename: `web-client.json`.
- Contents: содержимое скачанного JSON целиком.

Файл будет доступен приложению по `/etc/secrets/web-client.json`.
Не добавляйте JSON в GitHub и не вставляйте его в Build/Start Command.

В **Environment Variables** добавьте:

| Key | Value |
|---|---|
| `GOOGLE_CREDENTIALS_JSON` | `/etc/secrets/web-client.json` |
| `GOOGLE_TOKEN_FILE` | `/tmp/google-auth/token.json` |
| `GOOGLE_OAUTH_REDIRECT_URL` | `https://your-service.onrender.com/oauth/callback` |

`GOOGLE_OAUTH_REDIRECT_URL` должен точно совпадать с URI в Google Cloud.
Токен сохраняется отдельно от Secret Files: это выходной файл приложения,
которому нужен доступ для записи. `/tmp` здесь намеренно временное хранилище.

Для `-google-auth` **не нужны** `JIRA_TOKEN`, `GITLAB_TOKEN`, `SHEET_ID` и
остальные настройки tracker. Не переносите весь локальный `.env` для этого теста.

## 5. Выполните вход

1. Сохраните настройки и запустите **Manual Deploy → Deploy latest commit**,
   если сохранение настроек ещё не запустило деплой.
2. Дождитесь успешной сборки и откройте **Logs**.
3. Найдите последнюю строку:

   ```text
   Откройте приватную ссылку в своём браузере (действует 10 минут):
   https://your-service.onrender.com/oauth/start?key=...
   ```

4. После перехода сервиса в Live откройте **полную ссылку из текущего запуска**
   в своём браузере. Не публикуйте её: она даёт возможность подключить аккаунт
   к этому экземпляру сервиса. Не используйте её для health check.
5. Выберите добавленный в Test users аккаунт и разрешите запрошенный доступ.
6. Google вернёт браузер на адрес Render. Ожидаемый текст:

   ```text
   Google подключён. Можно закрыть вкладку. Результат работы смотрите в логах сервиса.
   Для записи в таблицу аккаунту нужны права редактора.
   ```

Этот ответ выдаётся **после успешного обмена кода на токен и сохранения файла**.
Это критерий успеха теста. SSH и просмотр содержимого токена не нужны.
Процесс затем завершится — так сейчас устроен одноразовый режим подключения.
Если Render перезапустит его, новая ссылка в логах относится уже к другому
сеансу. Для повторения теста используйте свежий запуск. После проверки
приостановите или удалите тестовый сервис.

## 6. Если не получилось

| Симптом | Что проверить |
|---|---|
| `redirect_uri_mismatch` | URI в Google Cloud и Render должны совпадать посимвольно, включая `https` и путь |
| Google сообщает, что доступ запрещён тестовому пользователю | Аккаунт добавлен в Test users; политики организации разрешают доступ |
| «Нужен JSON OAuth client типа Web application» | Загружен Web client, а не Desktop или service account |
| `No open ports detected` | Использована указанная Start Command с `0.0.0.0:$PORT` |
| Главная страница отвечает 404 | Это ожидаемо; открывайте приватную ссылку из Logs |
| «Недействительная ссылка» / «Недействительный сеанс входа» | Ссылка устарела после рестарта, отключены cookies или callback открыт в другом браузере |
| «Вход уже начат» | Сеанс одноразовый: повторите деплой и возьмите новую ссылку |
| В логах `context deadline exceeded` | Прошли 10 минут от старта процесса: повторите запуск |
| «Не удалось сохранить доступ» | Проверьте Web client, redirect URI и путь `/tmp/google-auth/token.json`; затем начните новый сеанс |
| После входа сервис остановился / перезапустился | Это ожидаемое завершение `-google-auth`, а не доказательство ошибки Google |

## 7. Что этот тест не проверяет

- Доступ к конкретной таблице и право изменять её.
- Сохранение авторизации после рестарта Render.
- Обновление access token после его истечения.
- Доступность корпоративных Jira и GitLab из сети Render.
- Почасовую обработку сред.

Проверка чтения таблицы и реального расчёта после входа доступна через
`-google-auth-run` (раздел 8). Запись в этом режиме запрещена. Внешнее хранилище
токенов для переживания рестартов пока не реализовано.

Free Web Service засыпает после 15 минут без входящих запросов; локальные файлы
теряются при перезапуске, деплое и засыпании. Постоянный диск и SSH на Free
недоступны. Поэтому текущий файловый токен и почасовой daemon нельзя считать
надёжным постоянным развёртыванием на бесплатном тарифе.

Режим Google External + Testing также ограничивает refresh token для Sheets
семью днями. Хостинг на Render это ограничение не отменяет.

## 8. Реальный прогон prod-holding на Render без записи

Этот режим выполняет вход и один прогон **в одном процессе**, после чего
сохраняет HTTP-сервер работающим. Он не планирует повторных прогонов и не
завершает процесс после результата или ошибки сбора. Перезапуск/засыпание Render
по-прежнему теряет временный токен; после нового запуска понадобится новый вход.

### Настройки

Отправьте свежий коммит ветки `google-server-oauth` в GitHub. В Render сохраните
существующий Secret File `web-client.json` и три переменные Google из раздела 4.
Замените **Start Command** на:

```bash
./env-release-tracker -google-auth-run -env prod-holding -google-auth-listen 0.0.0.0:$PORT
```

**Health Check Path:** `/health`. Ответ `ok` означает, что HTTP-сервер работает;
успех расчёта нужно смотреть в Logs.

Добавьте в Environment переменные (значения токенов вводите только в Render):

| Key | Value |
|---|---|
| `IMAGE_COLLECTOR` | `gitlab` |
| `GITLAB_URL` | `https://gitlab.metadoc.kz` |
| `GITLAB_TOKEN` | действующий токен с запуском пайплайнов и чтением результатов |
| `COLLECT_IMAGES_PROJECT_ID` | `234` |
| `COLLECT_IMAGES_REF` | `main` |
| `JIRA_URL` | `https://jira.metadoc.kz` |
| `JIRA_TOKEN` | действующий технический токен чтения Jira |
| `SHEET_ID` | ID копии реестра, доступной выбранному Google-аккаунту |
| `ENV_STATUSES` | `active` |
| `CONCURRENCY` | `1` |
| `STATE_FILE` | `/tmp/tracker-state.json` |

Остальные настройки имеют подходящие значения по умолчанию. В Render значения
вводятся без shell-кавычек. Если задаёте `JIRA_JQL`, вставляйте непосредственно
`summary ~ "Release" AND project = DevOps`, без внешних одинарных кавычек.

В копии таблицы должна присутствовать строка `prod-holding` со статусом `active`:
вкладка `gid=0`, строка 1 — заголовки, имя в A, статус в F, релиз в G.
Доступ Google-аккаунта на чтение достаточен. Проверьте, что это именно ID таблицы
из её URL между `/d/` и `/edit`, а не адрес целиком.

### Проверка

1. Выполните деплой с обновлённой веткой и настройками.
2. Откройте свежую приватную ссылку из Logs и подтвердите Google-доступ.
3. После сохранения токена прогон начнётся автоматически — отдельную команду
   запускать не нужно. Сервис прочитает Sheets и Jira, запустит настоящий
   collect-images для `prod-holding` и рассчитает релиз.
4. В Logs ожидаются сообщения:

   ```text
   Google подключён; запускается один проверочный прогон без записи
   ... пайплайн GitLab запущен ...
   ... релиз определён ... env=prod-holding ...
   ... dry-run: запись пропущена ...
   Проверочный прогон завершён; результат смотрите в логах
   HTTP-сервис остаётся запущенным. Автоматического повторного прогона нет
   ```

   Само сообщение о завершении ещё не доказывает расчёт: нужна строка
   `релиз определён` для `prod-holding`. Если `would_write=0` и такой строки нет,
   проверьте наличие среды, её статус, overrides и сообщения о пропусках.
5. Колонка G не изменится. `-write`, `-daemon`, отсутствие `-env` и `stub`
   для этого режима отклоняются до авторизации.
6. После проверки приостановите сервис. Для повторного теста перезапустите
   его и снова пройдите вход. Обновление страницы callback не повторяет прогон.

Если возникает ошибка Sheets, проверьте ID и доступ выбранного аккаунта.
Если Jira/GitLab возвращают 401/403 — проверьте токены и права. Если возникает
сетевой таймаут или ошибка DNS, проверьте доступность корпоративных адресов
из Render: доступ с вашего ноутбука через VPN не означает доступ из Render.
Не заменяйте сборщик на `stub`, чтобы выдать тестовые образы за реальный результат.
