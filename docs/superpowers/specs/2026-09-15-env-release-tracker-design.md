**Дата:** 2026-09-15
**Эпик:** DOPS-4919
**Статус:** черновик, ждёт утверждения заказчиком
**Источник требований:** `docs/task.txt`

---

## 1. Задача

Колонка `Release` в реестре сред заполняется руками и врёт: почти везде `release 57/3` или `release 59`, фактически стоит `Release 68 + HF`. Реальную версию каждый раз вычисляют вручную по тегам образов в кластере.

**Сервис на Go раз в час определяет релиз на каждой среде по тегам образов и проставляет его в колонку `Release` в виде `Release 68` или `Release 68 + HF`.**

### Что считается успехом

1. Колонка `Release` отражает фактическое состояние сред с задержкой не более часа.
2. Расхождения между тегами и Jira видны в логе, но не блокируют запись.
3. Сбой по одной среде не роняет прогон и не портит её значение в реестре.
4. Ошибочная запись в боевой реестр невозможна при отладке.

### Чего сервис не делает

- Не меняет ничего в Jira.
- Не трогает колонки реестра, кроме `G`.
- Не правит пайплайн `collect-images` (это отдельная задача DOPS-4919).
- Не имеет UI. Интерфейс — сам реестр.

## 3. Архитектура

### 3.1 Поток одного прогона

```
                      ┌──────────────────────────┐
                      │ 1. registry.List()       │
                      │ читает реестр сред       │
                      └────────────┬─────────────┘
                                   │ ~104 строки active|configuring
                                   ▼
                      ┌──────────────────────────┐
                      │ 2. overrides             │
                      │ skip / interval / env    │
                      └────────────┬─────────────┘
                                   │
                    ┌──────────────┴──────────────┐
                    │   worker pool, CONCURRENCY=5 │
                    └──────────────┬──────────────┘
                                   ▼
                      ┌──────────────────────────┐
                      │ 3. ImageCollector.Collect │
                      │ пайплайн → images.json    │
                      │ (fallback: разбор trace)  │
                      └────────────┬─────────────┘
                                   │ []tag.Tag
                                   ▼
┌───────────────────┐  ┌──────────────────────────┐
│ 4. jira.Baselines │─►│ 5. release.Compute        │
│ задачи Release/HF │  │ N = minor + 39, +HF       │
│ (только чтение)   │  └────────────┬─────────────┘
└───────────────────┘               │ Result
                                    ▼
                      ┌──────────────────────────┐
                      │ 6. registry.Update        │
                      │ один batchUpdate, кол. G  │
                      └──────────────────────────┘
```

Шаг 4 выполняется **один раз за прогон** до цикла по средам: базовые теги релизов общие для всех сред, дёргать Jira 104 раза незачем.

### 3.2 Пакеты

```
main.go                  флаги, сборка зависимостей, сигналы          ~150 строк
internal/
  app/        прогон: оркестрация шагов 1-6, worker pool              ~250
  config/     переменные окружения + overrides.yaml                   ~150
  tag/        разбор и сравнение тегов, нормализация имён сервисов    ~150
  registry/   реестр сред в Google Sheets: чтение и запись            ~300
  gitlab/     запуск пайплайна, артефакт, fallback на trace           ~300
  jira/       клиент только на чтение + разбор задач Release/HF       ~350
  release/    доменная логика: номер релиза и признак HF              ~200
```

Границы проведены по **источникам данных и по домену**: `tag` и `release` не знают ни про HTTP, ни про Sheets, и тестируются чистыми функциями. `registry`, `gitlab`, `jira` не знают про доменные правила.

### 3.3 Ключевой шов: `tag`

Теги приходят из **двух разных источников в разных форматах**:

| Источник | Пример |
|----------|--------|
| образ в кластере | `redo-backend:main-1.29.13` |
| строка `Projects:` в Jira | ` # backend: main-1.29.0` |

Семантика одна, поэтому разбор и сравнение живут в одном пакете — иначе правила нормализации разъедутся по кодовой базе. Это и есть требование DRY в самом опасном месте проекта.

```go
// Version — версия из тега. Suffix хранит cherry-pick: main-1.28.1-mcp4-8164.
type Version struct {
    Major, Minor, Patch int
    Suffix              string
}

// Tag — сервис и его версия, независимо от источника.
type Tag struct {
    Service string  // нормализованное имя образа: redo-backend
    Branch  string  // main, release или пусто
    Version Version
    Raw     string  // исходная строка, для логов и разбора инцидентов
}

func ParseImage(s string) (Tag, error)        // redo-backend:main-1.29.13
func ParseProjectLine(s string) (Tag, bool, error) // строка секции Projects
func NormalizeService(name string) string     // backend -> redo-backend
func (v Version) Compare(o Version) int
```

`ParseProjectLine` возвращает `bool`: строка может быть валидной, но намеренно пропускаемой — зачёркнутый сервис или пустой тег. Это не ошибка, и отличать её от ошибки разбора нужно явно.

### 3.4 Шов для вопроса A4

```go
// EnvState — снимок среды: что реально стоит в её namespace.
// Живёт в release, потому что это вход доменного расчёта, а не деталь GitLab.
type EnvState struct {
    Environment string
    Namespace   string
    Tags        []tag.Tag  // разобранные теги образов
    Unparsed    []string   // образы с чужой схемой тегов — в детали, не в расчёт
    CollectedAt time.Time
}

// ImageCollector снимает теги образов со среды.
type ImageCollector interface {
    Collect(ctx context.Context, environment string) (release.EnvState, error)
}
```

Пустой `Tags` — всегда ошибка, а не «релиза нет»: см. §6.3.

Реализация сейчас одна — через пайплайн GitLab. Если 2500 пайплайнов в сутки окажутся неприемлемы, добавляется вторая (прямой read-only доступ к кластеру или один пайплайн на все namespace), и `app` не меняется.

## 4. Доменные правила

### 4.1 Номер релиза

Теги кор-сервисов имеют вид `main-1.<minor>.<patch>`. Релиз двигает minor, HF — patch.

```
Release N  ⟷  minor = N − RELEASE_MINOR_OFFSET     (offset = 39)
```

**Кор-сервисы:** `redo-nuxeo`, `redo-backend`, `redo-camunda`, `redo-front`, `redo-integration`.

Алгоритм:

1. Если у сервиса в подах **два тега** (идёт накатка) — берём **больший**.
2. `N = minor + 39` по кор-сервисам.
3. minor у кор-сервисов **разный** → берём **меньший**, ставим флаг `MinorMismatch` **(допущение A1)**.
4. Кор-сервисов в namespace не нашлось → релиз не определён, значение в колонке не трогаем.

### 4.2 Признак `+ HF`

`+ HF`, если хотя бы один сервис новее своего тега в задаче `Release N`:

| Тип сервиса | Правило |
|-------------|---------|
| **кор-сервис** | `patch` выше базового тега из задачи. Задачу не нашли → выше `0` |
| **не-кор сервис** | тег новее, чем у него в задаче `Release N`. **Правило N−39 не применяется** — у них своя нумерация (в Release 67: `redo-email main-1.9.6`, `redo-event main-1.24.0`). Только сравнение с Jira. Нет в задаче → на HF не влияет, идёт в детали |

В расчёте участвуют все сервисы namespace с тегом `main-1.x.y` или `release-1.x.y`, включая суффикс cherry-pick. Образы с другой схемой (`redo-ai`, `busybox`, инфраструктура) в расчёт не входят, но попадают в детали.

### 4.3 Сверка с Jira

Проверяем: задача `Release N` существует; базовые теги кор-сервисов совпадают с `main-1.(N−39).base`; теги с patch выше базы встречаются в каком-либо HF после `Release N`.

**Несовпадение → предупреждение в лог и флаг расхождения. Значение всё равно записывается.** Сверка — диагностика, а не право вето: лучше записать значение с пометкой, чем оставить заведомо устаревшее.

### 4.4 Результат

```go
type Result struct {
    Environment   string
    Release       int       // 68
    HasHF         bool
    MinorMismatch bool      // кор-сервисы на разных minor
    JiraMismatch  bool      // сверка не сошлась
    Details       []string  // необъяснённые образы, пропуски, причины
    CollectedAt   time.Time
}

func (r Result) Cell() string   // "Release 68 + HF"
```

`Cell()` — единственное место, где результат превращается в текст ячейки. Формат HF (вопрос ТЗ №4) и показ cherry-pick (вопрос №6) меняются правкой одной функции.

## 5. Разбор данных Jira

Конвенцию для задач накатки не вводят, JQL остаётся как есть. Отличать релизные задачи от шума — задача сервиса.

**JQL:** `summary ~ "Release" AND project = DevOps` — сейчас 447 задач.

### 5.1 Правила очистки

| Особенность | Обработка |
|-------------|-----------|
| `backend:` против `redo-backend:` | нормализовать к имени образа |
| зачёркнутая строка `-текст-` | пропустить, сервис исключён |
| пустой тег `esedo-gateway:` | пропустить |
| жирный текст `*Projects:*` | снять разметку |
| хвост-комментарий после тега | взять первый токен |
| несколько блоков `Environments` + `Projects` | разные теги на разные среды |

Последний пункт — не мелочь. В DOPS-4820 основной поток идёт на `main-1.29.0`, а `prod-holding` и `prod-idfrk` — на `release-1.29.1`. Поэтому базовые теги хранятся как:

```go
type ReleaseTask struct {
    Key     string
    Number  int
    IsHF    bool
    Date    time.Time              // поле Date из описания, иначе created
    EnvTags map[string][]tag.Tag   // "" — основной поток, иначе имя среды
}
```

При сверке для среды сначала ищем её собственный блок, потом основной поток.

### 5.2 Отсев шума

Под JQL попадает: «Main / Release: проставить всем пользователям единый пароль», «Включить конфиг ... на release», «Release PLAT-7484 для сред ...».

Признаки настоящей релизной задачи (не исчерпывающе, по ТЗ):

- в заголовке номер релиза или HF;
- в описании есть секция `Projects` хотя бы с одним разбираемым тегом;
- статус `Done`;
- тег согласуется с правилом `minor = N − 39`.

**Непонятная задача не роняет прогон** — пропуск и запись в лог с ключом задачи и причиной, чтобы список исключений можно было дописать руками.

> **Замечание по надёжности.** Статус фильтруем по `statusCategory`, а не по имени: имена локализованы, в разных снимках встречались и `Done`, и `ГОТОВО`.

## 6. Сбор образов

### 6.1 Основной путь

1. `POST /api/v4/projects/234/pipeline` с `ref=main` и переменной `ENVIRONMENT`.
2. Опрос статуса пайплайна до завершения, таймаут **10 минут**.
3. Скачивание артефакта `images.json` джобы `collect-images`.

```json
{
  "environment": "prod-qazsu",
  "namespace": "prod-qazsu",
  "collected_at": "2026-09-15T10:00:00Z",
  "images": ["redo-backend:main-1.29.13", "redo-front:main-1.29.20"]
}
```

### 6.2 Fallback: разбор trace

До выкатки DOPS-4919 артефакта нет, результат только в логе джобы. Забираем trace и парсим JSON-массив после строки `Namespace: <ns>`. Строка `(no images found)` — пустой namespace.

Выбор пути автоматический: нет артефакта → trace. **(допущение C)**

### 6.3 Ошибки

| Ситуация | Поведение |
|----------|-----------|
| пайплайн упал | среда помечена «не удалось снять», значение не трогаем |
| таймаут 10 минут | то же, прогон продолжается |
| namespace пустой | то же |
| **ошибка доступа к namespace** | **текущий скрипт не отличает её от успеха** — приходит пустой список. Трактуем пустой список как ошибку, а не как «релиза нет» |

Последняя строка важна: принять ошибку доступа за пустую среду — значит затереть верное значение в реестре. Пустой результат никогда не приводит к записи.

## 7. Запись в реестр

**Таблица:** вкладка `gid=0`, диапазон `A:I`.
Колонки: `A` Наименование, `B` Домен, `C` Очередь накатки, `D` Тип среды, `E` Размещение, `F` Статус, `G` **Release**, `H` Менеджер, `I` Superset.

Правила:

1. **Один `batchUpdate` за прогон**, только ячейки колонки `G` обработанных строк.
2. Писать по номеру строки **из того же прогона**.
3. **Перед записью сверять имя в колонке `A`** — таблицу правят руками, строки могли сдвинуться. Имя не совпало → пропуск и запись в лог.
4. Значение не изменилось → не писать.
5. Остальные колонки не трогать.
6. Значения экранируются, чтобы Sheets не принял их за формулу (как `escapeFormulas` в backup-report).

### 7.1 Грабли реестра

- Неполный: `prod-jquo`, `prod-tedu`, `prod-techno-standart` есть в задачах накатки, но не в реестре; у `prod-avtopark`, `prod-qazaqcreative`, `prod-ws` статус пустой; `prod-cloud` в статусе `archive`, но получает HF.
- Дубли: `prod-sz` трижды, `prod-forensic` дважды (у лишних строк статус пустой).
- `prod-devops` в реестре `active`, но выключена.

**Дубли обрабатываем как есть:** по статусу проходит только одна строка, остальные с пустым статусом отсеиваются фильтром `ENV_STATUSES`. Сервис не чинит реестр — это вопрос ТЗ №13.

### 8.1 overrides.yaml

```yaml
envs:
  sk-prod:
    tags_name: "<раннер SK>"
  prod-devops:
    skip: "среда выключена"
  dev:
    skip: "офисная среда, теги веток"
  nit-adilet:
    interval: "24h"
```

- `environment` — что передать в collect-images вместо имени из реестра;
- `tags_name` — принудительный раннер. **Проверить на нашей инсталляции:** по документации GitLab переменные при запуске приоритетнее `workflow:rules:variables`;
- `skip` — не опрашивать, причина в лог, значение не трогаем;
- `interval` — опрашивать реже раза в час.

**Namespace через переменную не переопределить:** шаблон `set-namespace-before-script` выставляет `NS` в `before_script` и перетирает переданное. Нестандартный namespace — правилом в шаблоне или через `environment`.

Кандидаты: `sk-prod`, `prod-devops`, офисные `dev`/`main`/`hf-main`/`sprint`/`release`, `kegoc-test`, среды `nit` в статусе configuring.

### 8.2 Флаги

| Флаг | Назначение |
|------|------------|
| `-config` | путь к `overrides.yaml` |
| `-write` | **разрешить запись в таблицу.** Без него прогон только считает и пишет в лог |
| `-env <имя>` | одна среда, для отладки |
| `-daemon` | не выходить, ждать по расписанию **(допущение A3)** |

## 9. Безопасность

| Слой | Риск | Защита |
|------|------|--------|
| Токены | Утечка в git или логи | Vault; `.env` в `.gitignore`; маскирование `Authorization` в логах + тест |
| **Jira** | **Случайное изменение данных** | **Белый список эндпоинтов в `http.RoundTripper`.** `PUT`/`PATCH`/`DELETE` и `POST` вне списка не уходят в сеть. Тест: `DELETE /rest/api/2/issue/X` возвращает ошибку и не делает сетевого вызова |
| **Боевой реестр** | **Запись при отладке** | В конфиге разработки только id копии. Боевой id нигде в репозитории не хранится |
| `testdata/` в git | Реальные данные навсегда в истории | Санитайзер перед коммитом: ключи задач → `PROJ-1`, имена и домены → заглушки |
| Запись в Sheets | Затереть чужую правку | Сверка имени в колонке `A`; только колонка `G`; не писать, если не изменилось |
| GitLab | Перегрузка раннеров | `CONCURRENCY=5`, таймаут 10 минут, `interval` в overrides |

Белый список для Jira:

```
GET  /rest/api/2/field
GET  /rest/api/2/issue/{key}
POST /rest/api/2/search
```

`POST /rest/api/2/search` — читающий вызов, поэтому правило «только GET» не подходит и защита строится по эндпоинтам.

## 10. Тестирование

Разработка идёт по TDD: сначала тест, потом реализация.

| Пакет | Как тестируется |
|-------|-----------------|
| `tag` | Чистые функции. Таблица случаев: `main-`, `release-`, без ветки (`onlyoffice...: 8.3.3`), cherry-pick, зачёркнутые, пустые, с хвостом-комментарием |
| `release` | Чистые функции. Сценарии: обычный релиз, `+ HF`, разные minor у кор-сервисов, нет кор-сервисов, не-кор сервис вне задачи Release |
| `jira` | `httptest` с обезличенными ответами из `testdata/`. Отдельно — тест read-only guard |
| `gitlab` | `httptest`: успешный пайплайн, падение, таймаут, отсутствие артефакта → fallback на trace, `(no images found)` |
| `registry` | `httptest`: чтение, фильтр по статусу, дубли, сдвиг строк (имя в `A` не совпало), «значение не изменилось → не пишем» |
| `app` | Подставные реализации интерфейсов. Проверяем: сбой одной среды не роняет прогон; при ошибке сбора запись не идёт; `-dry-run` не пишет |

**Golden files** — обезличенные выгрузки в `testdata/`, как в backup-report. Тесты идут без сети и без доступа к Jira, GitLab и Google.

## 11. Порядок реализации

Снизу вверх: домен без зависимостей → клиенты → оркестрация.

1. `tag` — разбор и сравнение. Самостоятелен, тестируется полностью.
2. `release` — доменные правила поверх `tag`. Всё ещё без сети.
3. `config` — переменные окружения и `overrides.yaml`.
4. `jira` — клиент с read-only guard и разбор задач.
5. `gitlab` — запуск пайплайна, артефакт, fallback.
6. `registry` — чтение и запись реестра.
7. `app` — оркестрация, worker pool, обработка ошибок.
8. `main.go` — флаги и сборка зависимостей.
9. Dockerfile, пример `overrides.yaml`, README.

Первые два шага дают работающее ядро, проверяемое на реальных примерах из ТЗ, ещё до того, как появится доступ к GitLab и Google.
