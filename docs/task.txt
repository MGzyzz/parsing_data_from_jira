Суть: Нет достоверного источника, какой релиз стоит на какой среде. Колонка Release в реестре сред заполняется руками и неактуальна: почти везде написано release 57/3 или release 59, хотя фактически стоит Release 68 + HF. Реальную версию каждый раз вычисляют вручную по тегам образов в кластере. Из-за этого теряется время перед накаткой и при разборе инцидентов, реестр нельзя использовать как источник правды по версиям, и нельзя быстро ответить заказчику, что стоит на среде.

Задача: Сделать отдельный сервис на Go, который раз в час определяет релиз на каждой среде по тегам образов и сам проставляет его в колонку Release реестра сред в виде Release 68 или Release 68 + HF.

Задачи эпика:

DOPS-4919 — collect-images: сохранять список образов в артефакт images.json
Как работает (один прогон)
Читает реестр сред, берёт строки со статусом active или configuring (сейчас около 104 сред: 53 active и 51 configuring, из них 47 — среды nit).
По каждой среде запускает пайплайн collect-images и получает список образов с тегами.
Вычисляет номер релиза по тегам кор-сервисов, «+ HF» — по всем сервисам.
Сверяет результат с релизами из Jira.
Записывает результат в колонку Release реестра.

Релизы (Jira)

Роль Jira — сверка и базовые теги релизов. Сам номер релиза считается из тегов.
JQL (сейчас 447 задач):
summary ~ "Release" AND project = DevOps
Доступ — отдельный технический токен, не личный.
Заголовки: релиз — Release 68 ..., Release 57/3 ...; хотфикс — HF Release 11 Сентября ..., HF ... Release 12 Июня BAITEREK.
Теги берутся из секции Projects в описании задачи. Пример — DOPS-4820 (Release 68):
*Projects:*
 # nuxeo: main-1.29.0
 # backend: main-1.29.0
 # camunda: main-1.29.0
 # front: main-1.29.0
 # integration: main-1.29.0
 # esedo-gateway:
 # notification: main-1.29.0
 # -enbek-integration: main-1.29.0-
 # redo-email: main-1.29.0
У HF в Projects только изменённые сервисы (DOPS-4892: redo-backend main-1.29.13, redo-camunda main-1.29.12).
Дата события — поле Date из описания, если его нет — created.
Грязные данные — решение за разработчиком. Лучшего источника релизов нет, конвенцию для задач накатки не вводим. JQL остаётся как есть, отличать нормальные релизные задачи от шума — задача сервиса. Особенности формата:

имена сервисов то короткие (backend:), то полные (redo-backend:) — нормализовать к имени образа;
зачёркнутые строки — сервис исключён, пропускать;
пустой тег — пропускать;
жирный текст вокруг строки — снимать разметку;
в одной задаче бывает несколько блоков Environments + Projects с разными тегами (DOPS-4820: основной поток на main-1.29.0, prod-holding и prod-idfrk — на release-1.29.1);
хвосты-комментарии после тега — брать только первый токен;
под JQL попадает шум: «Main / Release: проставить всем пользователям единый пароль», «Включить конфиг ... на release», «Release PLAT-7484 для сред ...».
За что можно зацепиться (не исчерпывающе):

в заголовке номер релиза или HF;
в описании есть секция Projects хотя бы с одним разбираемым тегом;
статус Done;
тег из Projects согласуется с правилом minor = N − 39;
непонятные задачи не роняют прогон — пропуск и запись в лог (ключ задачи и причина), чтобы список исключений можно было дописать руками.
Определение релиза
Правило. Теги — main-1.<minor>.<patch>. Релиз двигает minor, HF — patch. Release N соответствует minor = N − 39. Держится минимум с Release 59, но исключения возможны, поэтому Jira используется для сверки.

Релиз	Теги кор-сервисов
Release 59	main-1.20.x
Release 66	main-1.27.x
Release 67	main-1.28.x
Release 68	main-1.29.0
HF после Release 68	main-1.29.13 (backend), main-1.29.12 (camunda), main-1.29.20 (front)
Кор-сервисы катятся тегами на всех средах, номер релиза определяется только по ним: redo-nuxeo, redo-backend, redo-camunda, redo-front, redo-integration.

В расчёте участвуют все сервисы namespace с тегом вида main-1.minor.patch или release-1.minor.patch, в том числе с суффиксом cherry-pick (например, main-1.28.1-mcp4-8164): notification, keycloak, report-data, email, event, esedo-gateway и т.д. Образы с другой схемой тегов (сборки веток redo-ai, busybox, инфраструктура) в расчёт не входят, но попадают в детали.

Для среды:

если у сервиса в подах два тега (идёт накатка) — берём больший;
номер релиза: N = minor + 39 по кор-сервисам; если minor у кор-сервисов разный — берём меньший и помечаем расхождение;
«+ HF» — если хотя бы один сервис новее своего тега в Release N:
кор-сервис — patch выше базового тега из задачи Release N (если задачу не нашли — выше 0);
не-кор сервис — тег новее, чем у него в задаче Release N. Правило N − 39 к ним не применяется, у них своя нумерация (в Release 67: redo-email main-1.9.6, redo-event main-1.24.0, redo-calendar main-1.26.0), поэтому только сравнение с Jira. Если сервиса нет в задаче Release N — на HF он не влияет, пишется в детали.
Сверка с Jira: задача Release N существует; базовые теги кор-сервисов из неё совпадают с main-1.(N − 39).base; теги среды с patch выше базы встречаются в каком-либо HF после Release N. Несовпадение — предупреждение в лог и пометка о расхождении, значение всё равно записывается.

Особые случаи:

cherry-pick и release-теги (release-1.29.1, main-1.28.1-mcp4-8164) — релиз по minor, формат отображения открыт (см. вопросы);
офисные среды собираются из веток, их теги под правило не подходят;
пайплайн упал, раннер недоступен, namespace пустой — значение в колонке не трогать, зафиксировать ошибку.
Локальные помощники по проблемным средам
Для большинства сред достаточно передать системное имя из реестра. Для сред, где это не работает, в репо сервиса лежит файл overrides.yaml — точечные правила без правок в общих шаблонах:

envs:   sk-prod:     tags_name: "<раннер SK>"
  prod-devops:     skip: "среда выключена"
  dev:     skip: "офисная среда, теги веток"
  nit-adilet:     interval: "24h"
environment — какое значение передать в collect-images вместо имени из реестра;
tags_name — принудительно указать раннер. Переменные, переданные при запуске пайплайна, по документации GitLab приоритетнее workflow:rules:variables — проверить на нашей инсталляции;
skip — не опрашивать; в лог пишется причина, значение в таблице не трогается;
interval — опрашивать реже раза в час.
Namespace через переменную не переопределить: шаблон set-namespace-before-script выставляет NS в before_script и перетирает переданное значение. Нестандартный namespace закрывается правилом в шаблоне или через environment.

Кандидаты (проверить при разработке): sk-prod (в шаблонах нет правила, уйдёт на раннер kt), prod-devops (выключена, в реестре active), офисные dev, main, hf-main, sprint, release (теги веток), kegoc-test (проверить namespace), среды nit в статусе configuring (не развёрнуты, опрашивать реже).

Запись в реестр
Один batchUpdate за прогон, только ячейки колонки G у обработанных строк.
Писать по номеру строки из того же прогона, перед записью сверять имя в колонке A — таблицу могут править руками.
Если значение не изменилось — не писать. Остальные колонки не трогать.
Запуск
Раз в час.
Параллельность запуска пайплайнов ограничена, по умолчанию 5: около 104 пайплайнов в час, примерно 2 500 в сутки.
Таймаут на пайплайн — 10 минут; по истечении среда помечается «не удалось снять», прогон продолжается.
Режим dry-run: всё посчитать и вывести в лог, в таблицу не писать. Режим одной среды — для отладки.

Открытые вопросы
Нагрузка на раннеры: около 2 500 пайплайнов в сутки — нормально? Альтернативы: ходить в кластеры напрямую (read-only kubeconfig) или запускать collect-images один раз на все namespace кластера (скрипт принимает список через запятую).
Технические учётки: Jira-токен, GitLab-токен, Google service account — какие, есть ли уже.
Дробные релизы (57/2, 57/3): как выглядят в тегах, различать ли их или это Release 57 + HF.
Формат HF: достаточно «+ HF» или с датой последнего HF («Release 68 + HF 11 Сентября»).
Что писать, если кор-сервисы на разных minor.
Как показывать cherry-pick и release-теги (holding, idfrk, kegoc).
Офисные среды (dev, main, hf-main, sprint, release): пропускать, писать прочерк или сырой тег backend.
Среды nit в статусе configuring — как часто опрашивать.
Ошибка сбора: оставлять старое значение? Добавить в реестр колонки «Проверено» и «Детали»?
Колонку Release после запуска правит только сервис, люди её не трогают?
Где крутится сервис: k8s CronJob или долгоживущий сервис с планировщиком и /metrics; в каком кластере; имя репо (например, redo/devops-tools/env-release-tracker).

Среды вне реестра (prod-jquo, prod-tedu, prod-techno-standart и др.) — добавить в реестр до запуска сервиса.
